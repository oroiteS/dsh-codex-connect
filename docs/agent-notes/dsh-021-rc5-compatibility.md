# DSH 0.2.1-rc.5 compatibility candidate

The desktop Host was upgraded to `0.2.1-rc.5` on 2026-10-30. The published Alpha 10 gate ends at exact `0.2.1-rc.3`, so the unchanged plugin is refused at load time. This candidate adds only exact `0.2.1-rc.5`, mirroring the focused rc.3 admission (#388): no other version, flag, default or runtime behavior changes.

## Published artifact review

Observed npm artifacts, not a Git-source claim. All twenty gated DSH peers plus the optional `dsh-commands` peer were downloaded from `registry.npmjs.org` at both `0.2.1-rc.3` and `0.2.1-rc.5` and compared structurally:

- `0.2.1-rc.4` exists on npm for all twenty packages; it is **not** declared. No evidence was produced for it and the actual Host is rc.5.
- Zero removed exported type symbols across every `lib/**/*.d.ts` in all twenty packages.
- Zero removed files; no `exports` map key changes; no dependency key-set changes.
- Additions are refused by design: only exact declared hosts are accepted.

The comparison script and its full per-package JSON report were one-off local evidence and are not committed; the summary above is the retained record. The method matches the rc.3 review (registry artifacts bound the comparison, GitHub tags do not).

## Scope

Changed only the declaration surface and its gates:

- `src/compatibility-policy.ts`: append exact `0.2.1-rc.5` to `SUPPORTED_DSH_PLUGIN_API_VERSIONS` (packaged `compatibility.json` mirrors it).
- `package.json`: append exact `0.2.1-rc.5` to the twenty DSH peers; candidate version `0.2.0-alpha.11`.
- `scripts/check-compatibility.mjs`, `scripts/check-dsh-next-contract.mjs`: extended declared range fixtures.
- Tests: exact-version acceptance table and the declared-list pin in installation guidance.

Unchanged: `verified-compatibility.json`, `INSTALL.md`, `README.md` and `docs/README.zh.md`. Those are the published recommendation surface and change only after a release readback through the existing Alpha workflow; the published Alpha 10 / rc.3 pairing remains the installation guidance. The development SDK stays pinned at `0.1.7-rc.1`, the plugin-owned pi-ai stays `0.85.1`, and all defaults, permissions, cancellation and durability behavior are untouched.

## Validation record

Local Node 26.13.0 results for this candidate:

- `pnpm run lint`, `pnpm run typecheck`: pass.
- `pnpm run test`: 2,335 passed, 25 failed, 2 skipped. The 25 failures are pre-existing in the two native-compaction probe files; the same 25 fail on the unmodified HEAD in this environment (child processes launched with `--experimental-transform-types` exit 9 / `CHILD_REPORT_INVALID` under Node 26). One stale CLI snapshot header (`0.2.0-alpha.10` → `0.2.0-alpha.11`) was regenerated by the version bump; the regenerated snapshot differs only in that string.
- `pnpm run build`: pass; `pnpm run check:compatibility`: `compatible` with the range ending `|| 0.2.1-rc.5`.
- `node scripts/check-dsh-next-contract.mjs`: 76/76. `node scripts/check-canary-workflow.mjs`: 93/93 plus 20 multi-version scenarios; rc.5 is recognized as declared.
- `pnpm run pack:check`: validated 71 packed files. npm's default cache directory is not writable under this session's file sandbox, so the check ran with `npm_config_cache` pointing inside the workspace.

The real-Host check is the installation of this candidate into the running desktop profile (`install_bundle` from this checkout). Its result is recorded separately from these keyless fixtures.

## Limitations

- No npm publication, tag, push or `latest` change; `0.2.0-alpha.11` is an unreleased local candidate.
- The real-account/model, OAuth and Desktop visual acceptance for rc.5 remains a user-level check; keyless gates do not establish it.
- Exact `0.2.1-rc.4` stays undeclared without artifact evidence, and later rc/stable versions stay refused.
